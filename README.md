# Задание 5. Проверка ссылок

Дедлайн: 8 декабря, 23:59 по Москве. 10 баллов.

## 1. Задача

Перед публикацией документации CI обходит её и проверяет, что ссылки открываются. Почти всё время уходит на ожидание ответа сети, поэтому страницы нужно запрашивать одновременно, но сайты нельзя заваливать запросами, а отчёт должен быть готов к общему дедлайну сборки. Напишите проверку, которая обходит страницы от стартовых до заданной глубины, соблюдает оба лимита и возвращает отчёт в срок.

Страницы загружает выданный `PageFetcher`: ему передают URI, он возвращает HTTP-статус и список ссылок, при сетевой ошибке бросает `IOException`, при прерывании `InterruptedException`. В тестах и замере страницы имитируются локально, поэтому реализовать нужно только обход, то есть `LinkCheckerImpl`.

## 2. Контракт

### 2.1. Типы

Все классы в пакете `edu.hse.concurrency.links`. Сигнатуры выданных типов и тесты менять нельзя, свои классы добавлять можно.

| Тип | Что это |
|---|---|
| `CheckRequest` | Идентификатор проверки, стартовые URI, глубина, общий таймаут и два лимита |
| `PageFetcher` | Загружает одну страницу; при прерывании прекращает работу |
| `Page` | HTTP-статус и ссылки со страницы, в том числе относительные |
| `LinkResult` | Глубина, исход проверки и HTTP-статус, если сервер его вернул |
| `CheckReport` | Результаты по нормализованным URI и признак истёкшего таймаута |
| `CheckContext` | `ScopedValue` с идентификатором текущей проверки |

Конструктор `LinkCheckerImpl(PageFetcher)` запускает задачи в виртуальных потоках. Перегрузка `LinkCheckerImpl(PageFetcher, ThreadFactory)` создаёт потоки переданной фабрикой и нужна только для замера из раздела 4.

### 2.2. Термины

Проверкой называется один вызов `check(CheckRequest)`. Состояние обхода, лимиты и дедлайн принадлежат проверке, поэтому одновременные вызовы друг друга не видят.

Задачей называется проверка одной страницы: один вызов `fetch` и запись его исхода. Каждая задача работает в отдельном потоке.

Глубина страницы равна длине кратчайшего пути до неё от любой стартовой страницы. Стартовые страницы имеют глубину 0.

Ключом результата служит нормализованный URI. Его готовит выданный `PageUris`: он разрешает относительные ссылки от URI страницы, отбрасывает ссылки вне HTTP(S), убирает фрагмент и порт по умолчанию, приводит схему и имя хоста к нижнему регистру и заменяет пустой путь на `/`. Путь нормализуется через `URI.normalize()`, запрос сохраняется, поэтому `/page?id=1` и `/page?id=2` считаются разными ссылками.

### 2.3. Обход

`check` проверяет все достижимые страницы до `maxDepth` включительно. При `maxDepth = 0` проверяются только стартовые страницы. На нормализованный URI приходится не больше одного вызова `fetch` за проверку, а глубину нельзя уточнить повторной загрузкой, поэтому обход идёт по уровням: сначала все страницы глубины 0, затем 1 и так далее. Обход продолжается по ссылкам со страниц со статусом 2xx. На последнем уровне статус страницы записывается, её ссылки дальше не обходятся.

| Исход `fetch` | `LinkResult.Status` | `statusCode` |
|---|---|---|
| HTTP 2xx | `OK` | Полученный HTTP-статус |
| Остальные HTTP-статусы | `HTTP_ERROR` | Полученный HTTP-статус |
| `IOException` | `IO_ERROR` | `null` |

`fetch` бросает только `IOException` и `InterruptedException`, других исключений и `null` от него не бывает. Ошибка одной страницы не прерывает остальные проверки. Порядок результатов в отчёте произвольный. Пустой список стартовых страниц даёт пустой отчёт без таймаута.

### 2.4. Лимиты и идентификатор

В каждый момент в работе не больше `maxConcurrentRequests` вызовов `fetch` всего и не больше `maxRequestsPerHost` для одного хоста. Ключ хоста берётся из `URI.getHost()` нормализованного URI, схема и порт на лимит не влияют. Задача, ожидающая разрешения для своего хоста, не занимает общий слот.

Внутри каждого вызова `fetch` код `PageFetcher` может прочитать `CheckContext.CHECK_ID.get()` и записать идентификатор в лог. Идентификатор должен соответствовать текущему `CheckRequest`, в том числе при одновременных вызовах `check`.

### 2.5. Таймаут и прерывание

`timeout` отсчитывается от начала `check` и охватывает весь обход, включая ожидание разрешений. При истечении срока отмените текущие задачи и верните `CheckReport` с `timedOut = true`. Если все уровни успели завершиться до истечения срока, `timedOut = false`. В отчёт входят ответы и ошибки ввода-вывода, полученные до дедлайна, у запросов, прерванных отменой, записи нет. `check` возвращается после завершения всех своих задач.

Если вызывающий поток прервали во время проверки, отмените её задачи и пробросьте `InterruptedException` после их завершения. Прерывание до начала `check` или при пустом списке стартовых страниц тоже даёт `InterruptedException`. Если срок истёк одновременно с прерыванием, приоритет у `InterruptedException`. Слот освобождается и при ошибке, и при прерывании.

### 2.6. Требования

1. `check` можно вызывать из любого числа потоков одновременно, вызовы независимы.
2. В отчёте у каждой страницы кратчайшая глубина, каждый нормализованный URI запрашивается один раз.
3. Ошибка одной страницы не мешает проверить остальные и попадает в отчёт отдельной записью.
4. Оба лимита соблюдаются, в том числе когда одновременно проверяются разные хосты.
5. К возврату из `check` ни одной задачи проверки не остаётся в работе, включая таймаут и прерывание.
6. `CheckContext.CHECK_ID` внутри запроса равен идентификатору его проверки.
7. Программа не зависает и не бросает исключений, которых нет в контракте.

## 3. Ограничения

### 3.1. Входные данные

| Что | Допустимо | Иначе |
|---|---|---|
| `checkId` | Непустая строка, содержащая непробельный символ | `IllegalArgumentException` |
| Стартовые URI | Абсолютные HTTP(S) URI с хостом, без логина и пароля, порт от 1 до 65 535 | `IllegalArgumentException` |
| `maxDepth` | Целое число от 0 | `IllegalArgumentException` |
| `timeout` | Больше нуля, до часа включительно | `IllegalArgumentException` |
| `maxConcurrentRequests`, `maxRequestsPerHost` | Целые числа от 1 | `IllegalArgumentException` |
| аргументы конструктора, `check` и `CheckRequest`, в том числе элементы списка стартовых URI | не `null` | `NullPointerException` |

Стартовые URI проверяет и нормализует сам `CheckRequest`, поэтому дубликаты схлопываются до вызова `check`. Допустимый статус `Page` лежит в диапазоне от 100 до 599.

### 3.2. Средства

Организуйте задачи через `StructuredTaskScope` из JDK 25, ограничьте вызовы `fetch` семафорами, передайте идентификатор через `ScopedValue`. Запрещены пулы потоков, `ThreadLocal` для идентификатора и циклы опроса. В тестах и замерах этих ограничений нет.

## 4. Замер

`threadProbe` трижды запускает один и тот же обход на виртуальных потоках и на платформенных. Заглушка возвращает со стартовой страницы 256 ссылок и задерживает каждый запрос на 30 мс, лимиты в обоих режимах одинаковы.

```bash
./gradlew threadProbe
```

Запишите время прогонов, укажите версию JDK и объясните, что ограничивает скорость в этом сценарии. Одинаковое время у двух режимов допустимо.

## 5. Оценка

Проект рассчитан на JDK 25, флаг `--enable-preview` Gradle передаёт сам. Запуск `./gradlew test`, в Windows `gradlew.bat test`. Решение проверяется, только если проект собирается, `LinkCheckerSmokeTest` проходит полностью и есть `REPORT.md` с ответами на вопросы раздела 6, иначе 0 баллов.

Критерии проверяются скрытыми тестами, в том числе с одновременными вызовами `check` и медленным `PageFetcher`. Критерий засчитывается, только если выполняется во всех прогонах, один сбой даёт 0, каждый критерий стоит 1 балл.

| # | Критерий |
|---|---|
| 1 | Обход до заданной глубины, в отчёте указаны кратчайшие расстояния до страниц |
| 2 | Относительные ссылки разрешаются, нормализованный URI проверяется один раз |
| 3 | На HTTP-ошибку и ошибку ввода-вывода создаётся запись, оставшиеся страницы проверяются |
| 4 | Соблюдаются оба лимита, в том числе при одновременной работе с разными хостами |
| 5 | Запросы идут в отдельных виртуальных потоках под `StructuredTaskScope` |
| 6 | По общему таймауту возвращается частичный отчёт, задач после возврата не остаётся |
| 7 | Прерывание вызывающего отменяет задачи, разрешения освобождаются |
| 8 | `ScopedValue` доступен в запросах и отражает идентификатор их проверки |
| 9 | Одновременные вызовы `check` независимы, входные ошибки обработаны |
| 10 | Есть замеры на обоих типах потоков и объяснение результатов |

Объяснить придётся любой критерий: если студент не может, критерий не засчитывается.
