# Задание 5. Проверка ссылок

Дедлайн — 12 декабря, 23:59 по Москве. 10 баллов.

## 1. Задача

Перед публикацией документации CI проверяет, что ссылки открываются. Проверка должна идти параллельно, соблюдать лимиты для каждого сайта и успевать вернуть отчёт в рамках общего дедлайна.

Реализуйте обход в `LinkCheckerImpl`. Загружает страницы выданный `PageFetcher`. Ему передают URI, а он возвращает HTTP-статус и список ссылок. В тестах и замере страницы имитируются локально.

## 2. Контракт

### 2.1. Типы

Все классы находятся в пакете `edu.hse.concurrency.links`. Сигнатуры выданных типов и тесты менять нельзя. Свои классы добавлять можно.

| Тип | Назначение |
|---|---|
| `CheckRequest` | Идентификатор проверки, стартовые URI, глубина, общий таймаут и два лимита |
| `PageFetcher` | Загружает одну страницу и реагирует на прерывание |
| `Page` | HTTP-статус и ссылки со страницы, в том числе относительные |
| `LinkResult` | Глубина, результат проверки и HTTP-статус, если сервер его вернул |
| `CheckReport` | Результаты по URI и признак истечения общего таймаута |

`LinkCheckerImpl(PageFetcher)` запускает задачи в виртуальных потоках. Перегрузка `LinkCheckerImpl(PageFetcher, ThreadFactory)` использует переданную фабрику для сравнительного замера.

### 2.2. Обход

`CheckReport check(CheckRequest request)` проверяет все достижимые страницы до `maxDepth` включительно. Стартовые страницы имеют глубину 0. Глубина остальной страницы — длина кратчайшего пути до неё от любой стартовой страницы. При `maxDepth = 0` проверяются только стартовые страницы.

Используйте выданный `PageUris`. Он разрешает относительные ссылки от URI страницы и отбрасывает ссылки вне HTTP(S). Ключ результата — нормализованный URI. У него нет фрагмента и порта по умолчанию, имя хоста и схема в нижнем регистре, а пустой путь заменён на `/`. Путь нормализуется через `URI.normalize()`. Запрос сохраняется, поэтому `/page?id=1` и `/page?id=2` — разные ссылки.

На нормализованный URI приходится не больше одного вызова `fetch` за проверку. Каждая задача запроса работает в отдельном потоке. Обход продолжается по ссылкам со страниц со статусом 2xx. На последнем уровне статус страницы проверяется, её ссылки дальше не обходятся.

| Исход `fetch` | Статус в `LinkResult` | `statusCode` |
|---|---|---|
| HTTP 2xx | `OK` | Полученный HTTP-статус |
| Остальные HTTP-статусы | `HTTP_ERROR` | Полученный HTTP-статус |
| `IOException` | `IO_ERROR` | `null` |

Ошибка одной страницы не прерывает остальные проверки. Порядок результатов в отчёте произвольный. Пустой список стартовых страниц даёт пустой отчёт без таймаута.

### 2.3. Лимиты и контекст

В каждый момент в работе не больше `maxConcurrentRequests` вызовов `fetch` всего и не больше `maxRequestsPerHost` для одного хоста. Ключ хоста — `URI.getHost()` нормализованного URI. Схема и порт на этот лимит не влияют. Задача, ожидающая разрешения для своего хоста, не занимает общий слот.

Внутри каждого вызова `fetch` код запроса может прочитать `CheckContext.CHECK_ID.get()` и записать идентификатор в лог. Идентификатор должен соответствовать текущему `CheckRequest`, включая одновременные вызовы `check`. Состояние обхода и лимиты принадлежат одной проверке.

### 2.4. Таймаут и прерывание

`timeout` отсчитывается от начала `check` и охватывает весь обход, включая ожидание разрешений. При истечении срока отмените текущие задачи и верните `CheckReport` с `timedOut = true`. В отчёт входят ответы и ошибки ввода-вывода, полученные до дедлайна. У запросов, прерванных отменой, записи в отчёте нет. `check` возвращается после завершения всех своих задач.

Если вызывающий поток прервали во время проверки, отмените её задачи и пробросьте `InterruptedException` после их завершения. Выданный `PageFetcher` прекращает работу при прерывании. Слот освобождается и при ошибке или прерывании.

## 3. Ограничения

| Что | Допустимо |
|---|---|
| `checkId` | Непустая строка, содержащая непробельный символ |
| Стартовые URI | Абсолютные HTTP(S) URI с хостом, без логина и пароля |
| `maxDepth` | Целое число от 0 |
| `timeout` | Больше нуля, до часа включительно |
| `maxConcurrentRequests` и `maxRequestsPerHost` | Целые числа от 1 |

Недопустимое значение даёт `IllegalArgumentException`. При `null` в аргументах конструктора, `check` или `CheckRequest`, в том числе в списке стартовых URI, бросается `NullPointerException`. Указанный порт должен лежать в диапазоне 1–65 535.

Организуйте задачи через `StructuredTaskScope` из JDK 25, ограничьте вызовы `fetch` семафорами, передайте идентификатор через `ScopedValue`. В решении запрещены пулы потоков, `ThreadLocal` для идентификатора и циклы опроса. В тестах и замерах этих ограничений нет.

## 4. Замер

`threadProbe` трижды запускает один обход на виртуальных и платформенных потоках. Заглушка возвращает 256 ссылок и имитирует задержку 30 мс на запрос. Лимиты одинаковы в обоих режимах.

```bash
./gradlew threadProbe
```

Запишите время прогонов и объясните, что ограничивает скорость в этом сценарии. Укажите версию JDK. Одинаковое время у двух режимов допустимо.

## 5. Оценка

Проект рассчитан на JDK 25. Gradle передаёт `--enable-preview` при компиляции и запуске. Тесты запускаются через `./gradlew test`, в Windows — `gradlew.bat test`.

Для проверки проект должен собираться, `LinkCheckerSmokeTest` должен проходить целиком, а в README должен быть отчёт из раздела 6. За каждый критерий — 1 балл. Преподаватель может попросить объяснить любой критерий.

| # | Критерий |
|---|---|
| 1 | Обход до заданной глубины, в отчёте указаны кратчайшие расстояния до страниц |
| 2 | Относительные ссылки разрешаются, нормализованный URI проверяется один раз |
| 3 | На HTTP-ошибку и ошибку ввода-вывода создаётся запись, оставшиеся страницы проверяются |
| 4 | Соблюдаются оба лимита, в том числе при одновременной работе с разными хостами |
| 5 | Запросы идут в отдельных виртуальных потоках под `StructuredTaskScope` |
| 6 | По общему таймауту возвращается частичный отчёт, задач после возврата не остаётся |
| 7 | Прерывание вызывающего отменяет задачи, разрешения освобождаются |
| 8 | `ScopedValue` доступен в запросах и отражает идентификатор их проверки |
| 9 | Одновременные вызовы `check` независимы, входные ошибки обработаны |
| 10 | Есть замеры на обоих типах потоков и объяснение результатов |
